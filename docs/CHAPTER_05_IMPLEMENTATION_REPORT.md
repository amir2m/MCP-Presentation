## ۳. مدل چرخه حیات ۸ مرحله‌ای (The 8-Step Lifecycle Model)

چرخه رفت و برگشت درخواست در شبیه‌ساز به شرح زیر مدلسازی شده است:

```
[گام ۱: کاربر -> Host]         طرح پرسش طبیعی درباره موجودی NVMe-4TB
       ↓
[گام ۲: Host -> LLM]           ارسال پرامپت + تعاریف پیش‌کشف‌شده ابزار (tools/list)
       ↓
[گام ۳: LLM -> Host]           استنتاج مدل و اعلام قصد فراخوانی ابزار (Model Tool Call)
       ↓
[گام ۴: Host -> MCP Client]    گیت امنیتی، اعتبارسنجی آرگومان‌ها و هدایت به آداپتور داخلی
       ↓
[گام ۵: Client -> MCP Server]  ارسال فریم رسمی JSON-RPC 2.0 با متد tools/call و فراداده _meta
       ↓
[گام ۶: Server -> External DB] اعتبارسنجی، اجرای هندلر داخلی و اجرای کوئری در پایگاه داده انبار
       ↓
[گام ۷: Server -> Client/Host] بازگشت پاسخ رسمی MCP با فیلد resultType: "complete" (یا شیء error)
       ↓
[گام ۸: Host -> LLM -> کاربر]  تزریق داده مستند به کانتکست مدل و سنتز پاسخ نهایی فاقد توهم آماری
```

## ۴. سناریوهای چهارگانه و تدقیق معنایی خطاها (Scenarios & Error Semantics)

برای تضمین بیشترین دقت علمی، چهار سناریوی متمایز با رفتارهای پروتکلی دقیق پیاده‌سازی شدند:

| سناریو | وضعیت کسب‌وکار | نوع پاسخ پروتکل | وضعیت فیلد `isError` | کد وضعیت | کلیدهای اصلی داده |
|---|---|---|---|---|---|
| **الف: موجود در انبار** | موفق (کالای موجود) | `result` استاندارد با `resultType: "complete"` | غایب / false | - | `in_stock: true, quantity: 6, inventory_id: "INV-2026-981"` |
| **ب: عدم موجودی کالا** | موفق (موجودی صفر) | `result` استاندارد با `resultType: "complete"` | غایب / false | - | `in_stock: false, quantity: 0, inventory_id: "INV-2026-981"` |
| **ج: خطای اجرای ابزار** | شکست منطق ابزار | `result` استاندارد با `resultType: "complete"` | `true` (الزام پروتکل) | - | `content[0].text`: شرح خطای قطعی دیتابیس / تایم‌اوت |
| **د: خطای سطح پروتکل** | عدم انطباق پروتکلی | شیء بالادستی `error` در JSON-RPC (بدون `result`) | فاقد شیء result | `-32601` | `code: -32601, message: "Method not found"` |

### تفکیک بنیادین علمی:
1. **موجودی صفر خطا نیست:** در سناریوی ب، اجرای ابزار کاملاً موفق بوده و مقدار عددی موجودی برابر با ۰ است. پروتکل این حالت را هرگز خطا قلمداد نکرده و فیلد `isError: true` ثبت نمی‌شود.
2. **خطای ابزار در برابر خطای پروتکل:** در سناریوی ج، فریم پروتکل معتبر است و ارتباط لایه JSON-RPC برقرار است؛ بنابراین خطا در درون شیء `result` با پرچم `isError: true` گزارش می‌شود تا مدل بتواند آن را به صورت منطقی تفسیر کند. اما در سناریوی د، متد ناشناخته است و لایه JSON-RPC مستقیماً شیء خطای بالادستی با کد `-32601` صادر می‌کند.

## ۵. بازرس فنی ۵ تبِ داده‌ای (Technical Payload Debugger)

دیباگر داده‌ای تعاملی با ۵ تب تخصصی به منظور مشاهده آناتومی دقیق پیام‌ها در هر لحظه طراحی شده است:

1. **تب ۱: قصد مدل (Illustrative Model Tool-Calling Representation):**  
   با بنر هشداردهنده که نشان می‌دهد این ساختار صرفاً نمایش نمونه از فرمت فراخوانی ابزار مدل‌های زبانی (نظیر OpenAI Function Calling، Anthropic Tool Use، یا Gemini Function Calling) است و متعلق به پروتکل MCP نیست.
2. **تب ۲: پیام پروتکلی (MCP JSON-RPC Request):**  
   فریم رسمی JSON-RPC 2.0 با متد `tools/call`، شناسه پایدار `req-042`، پارامترهای ابزار `query_inventory` و فراداده‌های الزامی `_meta` شامل `io.modelcontextprotocol/protocolVersion: "2026-07-28"` و `io.modelcontextprotocol/clientCapabilities: {}`.
3. **تب ۳: اجرای داخلی (Server Internal Execution):**  
   کد نمونه کوئری SQL استعلام انبار همراه با بنر تاکیدی بر اینکه سرور MCP یک آداپتور مستقل است و پروتکل هیچ وابستگی یا محدودیتی نسبت به دیتابیس ندارد (Database Agnostic).
4. **تب ۴: پاسخ پروتکل (MCP Result Payload):**  
   پاسخ استاندارد سرور با شناسه یکسان `req-042` و فیلد الزامی `resultType: "complete"`.
5. **تب ۵: پاسخ نهایی (Final Model Response):**  
   پاسخ طبیعی و روان فارسی که توسط مدل با تکیه بر شواهد دریافتی از ابزار تدوین شده و شناسه مرجع انبار را مستند می‌سازد.

## ۶. دوگانگی حالت ارائه و روایتی (Dual Mode Presentation)

- **حالت اسلاید (Slides Mode):**  
  ارائه اسلایدی تمام‌صفحه با نوار کنترل شناور، پایشگر زمان و شاخصگر فعال گام‌های ۶گانه. ترنزیشن‌های حرکتی روان بین اسلایدها با استفاده از Framer Motion بدون پرش صفحه یا شیفت محتوا.
