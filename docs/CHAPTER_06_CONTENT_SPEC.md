## ۱. نمای کلی و فلسفه فصل ششم (Chapter Overview & Philosophy)

در پنج فصل گذشته، ضرورت تعامل مدل‌های زبانی با دنیای خارج، ریشه‌های پیدایش یک پروتکل استاندارد، معماری و نقش‌های سه‌گانه MCP، و در نهایت چرخه حیات گام‌به‌گام یک درخواست واقعی با استعلام قطعه سخت‌افزاری <span className="font-mono text-cyan-300" dir="ltr">NVMe-4TB</span> به صورت عملیاتی تشریح گردید.

اما در این نقطه از ارائه، یک پرسش بنیادین و چالش‌برانگیز در ذهن هر مهندس نرم‌افزار، معمار سیستم و دانشجوی علوم کامپیوتر شکل می‌گیرد:
> **«اگر دهه‌هاست که APIها وجود دارند و سیستم‌های نرم‌افزاری را به بهترین شکل به یکدیگر متصل می‌کنند، چرا صنعت هوش مصنوعی به یک پروتکل جدید به نام MCP نیاز پیدا کرده است؟ آیا MCP قرار است جایگزین REST API شود؟»**

هدف محوری فصل ششم، **پاسخ علمی، دقیق و بدون تعصب به این پرسش کلیدی** است. این فصل نشان می‌دهد که گزاره «MCP در برابر API» یک مغالطه دسته‌بندی (Category Mistake) است؛ چرا که MCP هرگز جایگزین API نیست، بلکه یک **پروتکل باز و استاندارد در لایه ارتباطی برنامه‌های هوش مصنوعی** است که اتفاقاً می‌تواند همان REST APIها، پایگاه‌های داده و وب‌سرویس‌های موجود را در قالب سرورهای MCP کپسوله کرده و در اختیار برنامه‌های میزبان سازگار قرار دهد.

## ۲. اهداف آموزشی کلان (Learning Objectives)

پس از اتمام فصل ششم، مخاطبان قادر خواهند بود:
1. **تمایز مفهوم عام API از سبک معماری REST:** درک کنند که API مفهومی فراگیر برای قرارداد ارتباطی میان نرم‌افزارهاست و REST تنها یکی از سبک‌های طراحی API در بستر وب است؛ نه هر API لزوماً REST است و نه MCP جایگزین معماری وب محسوب می‌شود.
2. **کالبدشکافی جایگاه لایه‌ای MCP در برابر APIها:** توضیح دهند که سرورهای MCP چگونه می‌توانند با حفظ کامل REST APIهای موجود در سازمان، به عنوان یک آداپتور هوشمند عمل کرده و قابلیت‌های ابزاری، منابع داده‌ای و پرامپت‌ها را استانداردسازی نمایند.
3. **تحلیل چالش اتصالات اختصاصی تکراری (The M×N Integration Challenge):** تمایز بنیادین میان «تعداد روابط ارتباطی زمان اجرا (Runtime Connections)» و «تعداد واحدهای پیاده‌سازی قابل استفاده مجدد (Reusable Implementations)» را درک کنند. دریابند که در صورت اتصال کامل $M$ هاست به $N$ سرور، تعداد کانال‌های ارتباطی منطقی در زمان اجرا همچنان $M \times N$ است؛ اما معماری MCP با جایگزینی کانکتورهای اختصاصی پراکنده با $M$ کلاینت استاندارد و $N$ سرور مستقل ($M+N$ واحد پیاده‌سازی قابل بازاستفاده)، از تکثیر کدهای اتصال جلوگیری می‌کند (با تاکید بر اینکه مدل $M \times N$ یک مدل مفهومی و آموزشی برای درک مسئله تکثیر کد است، نه یک قانون قطعی ریاضی؛ و تعداد دقیق پیاده‌سازی‌ها تابع معماری، گیت‌وی‌ها و کتابخانه‌های مشترک است).
4. **تفکیک قطعی Function Calling از پروتکل MCP:** مرزبندی کنند که فراخوانی تابع (Function Calling) یک سازوکار مابین مدل و برنامه میزبان (Model-to-Host) است؛ در حالی که MCP پروتکل ارتباطی استاندارد میان کلاینت و سرور (Client-to-Server) است و این دو فناوری کاملاً مکمل یکدیگرند.
5. **کاربرد چارچوب تصمیم‌گیری مهندسی (Decision Framework):** با معیارهای عینی تشخیص دهند که چه زمانی یک اتصال مستقیم REST API ساده‌ترین و بهترین گزینه است، و چه زمانی استفاده از لایه سرور MCP ارزش افزوده و صرفه مهندسی ایجاد می‌کند.

## ۴. مرزبندی‌های علمی غیرقابل‌مذاکره (Non-Negotiable Scientific Demarcations)

برای تضمین بیشترین دقت علمی در ارائه، اصول هفت‌گانه زیر در تمامی بخش‌ها، اسلایدها و یادداشت‌های سخنران حاکم هستند:

### ۴.۱. تفکیک مفهوم عام API از سبک معماری REST و دقت OpenAPI
* **API (Application Programming Interface):** یک قرارداد و اینترفیس عمومی است که به دو مولفه نرم‌افزاری اجازه می‌دهد بدون نیاز به آگاهی از جزییات پیاده‌سازی داخلی، با یکدیگر تبادل داده و فراخوانی عملیات داشته باشند. این مفهوم شامل کتابخانه‌های محلی، توابع سیستمی (POSIX)، GraphQL، gRPC، SOAP و وب‌سرویس‌ها می‌شود.
* **REST (Representational State Transfer):** یک سبک معماری خاص (نه صرفاً چند متد HTTP و URL) است که توسط روی فیلدینگ در سال ۲۰۰۰ بر پایه منابع (Resources)، شناسه‌های یکتا (URI)، متدهای استاندارد انتقال وضعیت (مانند GET, POST, PUT, DELETE) و تعاملات بدون حالت (Stateless) صورت‌بندی شد.
* **دقت در خصوص قراردادها و OpenAPI:** هرگز نباید القا شود که REST APIها فاقد ساختار ماشین‌خوان یا مستندات استاندارد هستند. مشخصات OpenAPI (OAS) سال‌هاست که به عنوان فرمت استاندارد تعریف قرارداد و شمای وب‌سرویس‌های HTTP عمل می‌کند. چالش بنیادین در تعامل مدل‌های زبانی، نبودِ مستندات در REST نیست، بلکه نبودِ یک پروتکل تعاملی دینامیک، قرارداد یکپارچه کشف قابلیت‌ها در سطح ایجنت‌ها، و تکثیر کدهای نگاشت اختصاصی در برنامه‌های مختلف میزبان هوش مصنوعی است.
* **اصل ارائه:** نباید از واژه‌های «API» و «REST API» به عنوان مفاهیم مترادف استفاده شود، و نباید ارائه به یک کلاس آموزش جزییات REST تبدیل گردد.

### ۴.۲. رابطه هم‌افزا میان API و MCP (عدم جایگزینی)
* پروتکل MCP **جایگزین API نیست** و نباید به عنوان رقیب حذف‌کننده REST معرفی شود.
* یک سرور MCP در لایه درونی خود (Internal Implementation) می‌تواند به عنوان یک آداپتور عمل کرده و دقیقاً همان REST APIهای شرکتی، پایگاه‌های داده SQL/NoSQL، SDKهای زبان‌های مختلف، یا حتی ابزارهای خط فرمان (CLI) را فراخوانی نماید.
* سیستم‌ها و APIهای بک‌اند سازمان نیازی به بازنویسی ندارند؛ بلکه با افزودن یک سرور MCP روی آن‌ها، این قابلیت‌ها به زبانی که برنامه‌های سازگار با MCP می‌فهمند (ابزارها، منابع و پرامپت‌ها)، اکسپوز می‌شوند.
* **ساده‌سازی آموزشی مجاز:** نباید ادعا شود که MCP به صورت خودکار یا جادویی هر API را تبدیل به ابزار هوش مصنوعی می‌کند؛ ایجاد و تنظیم سرور MCP یا کامپوننت متناظر برای اکسپوز کردن قابلیت‌ها همچنان نیازمند توسعه و پیکربندی است.

### ۴.۳. تفکیک معماری Function Calling از پروتکل MCP
* **Function Calling (یا Tool Calling):** مکانیسمی اختصاصی در سطح مدل زبانی است. مدل پرامپت و تعاریف شمای ابزار را دریافت می‌کند و به جای متن عادی، یک ساختار داده‌ای استاندارد تولید می‌کند که نشان می‌دهد مایل است فلان تابع با فلان آرگومان‌ها فراخوانی شود. مدل خود تابع را اجرا نمی‌کند؛ این وظیفه برنامه میزبان (Host) است.
* **Model Context Protocol (MCP):** پروتکلی در سطح کلاینت و سرور است که پیام‌های استاندارد JSON-RPC 2.0 را روی ترابری‌های مستقل (STDIO یا HTTP) میان برنامه میزبان و سرورهای خارجی مبادله می‌کند و مفاهیمی چون ابزارها (Tools)، منابع داده‌ای (Resources) و پرامپت‌ها (Prompts) را استانداردسازی می‌نماید.
* **همکاری در عمل:** هاست ابزارهای سرور MCP را به عنوان توابع قابل فراخوانی به مدل معرفی می‌کند؛ مدل خروجی Function Calling می‌دهد؛ هاست آن را اعتبارسنجی می‌کند؛ کلاینت MCP درخواست `tools/call` را به سرور می‌فرستد؛ سرور اجرا می‌کند و نتیجه را برمی‌گرداند؛ و هاست داده را برای مدل فراهم می‌سازد.
* **اصل اکید:** خروجی Function Calling مدل به خودی خود هرگز یک فریم پروتکل MCP JSON-RPC نیست!

### ۴.۴. مدل مفهومی اتصالات چندگانه: تفکیک اتصالات زمان اجرا از واحدهای پیاده‌سازی (M×N vs M+N)
* **تعداد روابط زمان اجرا (Runtime Connections):** اگر $M$ برنامه میزبان هوش مصنوعی (مانند Claude Desktop، یک IDE، و یک ایجنت مستقل) بخواهند به صورت هم‌زمان به $N$ سرور مستقل MCP متصل شوند، تعداد اتصالات و کانال‌های ارتباطی منطقی فعال در زمان اجرا همچنان $M \times N$ است (مثلاً $3 \times 3 = 9$ اتصال فعال). پروتکل MCP تعداد ارتباطات فیزیکی یا منطقی زمان اجرا را به ۳ اتصال کاهش نمی‌دهد!
* **تعداد واحدهای پیاده‌سازی قابل استفاده مجدد (Reusable Implementations):** در روش‌های سنتی سفارشی (Ad-hoc)، هر برنامه برای هر وب‌سرویس نیازمند یک کد اتصال چسباننده (Glue Code) اختصاصی است؛ یعنی در حالت تئوریک نیازمند $M \times N$ پیاده‌سازی مجزا و ناهماهنگ هستیم. اما در معماری MCP، این چالش به $M + N$ واحد پیاده‌سازی مستقل و استاندارد تبدیل می‌شود: $M$ پیاده‌سازی کلاینت MCP سازگار در برنامه‌های میزبان و $N$ سرور مستقل MCP. هر کلاینت استاندارد می‌تواند به هر سرور استانداردی متصل شود.
* **وابستگی به معماری واقعی:** شمار دقیق پیاده‌سازی‌ها در سیستم‌های واقعی به معماری سازمان، استفاده از کتابخانه‌ها و SDKهای مشترک، استقرار گیت‌وی‌ها (Gateways) و الگوهای بازاستفاده کد وابسته است.
* **قید الزامی علمی:** مدل $M \times N$ یک «مدل مفهومی و آموزشی برای مصورسازی مسئله تکثیر کدهای اختصاصی» است، نه یک قانون قطعی ریاضی جهان‌شمول در MCP.

### ۴.۵. تداوم سناریوی استاندارد آموزشی پروژه
* برای مقایسه مستقیم، دقیقاً از همان سناریوی باسابقه ارائه استفاده می‌شود:
  - **قطعه سخت‌افزاری:** `NVMe-4TB`
  - **موجودی نمونه انبار:** `6` عدد
  - **شناسه رکورد انبار:** `INV-2026-981`
* با حفظ این سناریو، مخاطب در هر دو معماری (اتصال مستقیم API در برابر اتصال مبتنی بر سرور MCP) مشاهده می‌کند که نتیجه کسب‌وکار یکسان است و تنها مرز اتصال و قابلیت استفاده مجدد تغییر کرده است. از خلق فیلدها و اسامی ناشناخته انبار خودداری می‌شود.

### ۴.۶. قلمرو و مرزهای مکانیزم کشف در نگارش 2026-07-28 (Discovery Scope & Boundaries)
* **متد `server/discover`:** در مشخصات مصوب 2026-07-28، سرورها الزامی است (MUST) متد `server/discover` را برای اعلام هویت، نسخه و قابلیت‌های کلی سرور پیاده‌سازی کنند. کلاینت‌ها مجازند (MAY) پیش از شروع سایر تعاملات این متد را برای کشف اولیه فراخوانی نمایند.
* **کاتالوگ‌های `tools/list` و `resources/list`:** جزییات دقیق ابزارهای قابل اجرا و منابع داده‌ای از طریق این متدها اکسپوز می‌شوند.
* **کشف، جایگزین طراحی و مستندسازی نیست:** وجود قابلیت کشف خودکار ماشینی هرگز نیاز به طراحی دقیق شمای ابزارها (Input Schemas)، نگارش توضیحات رسا و دقیق برای هدایت مدل (Descriptions)، مستندات و راهنماهای فنی انسانی، و تنظیم سیاست‌های شفاف احراز هویت و مجوزدهی (Authorization Policies) را برطرف نمی‌کند. پروتکل کشف تنها زبان مبادله کاتالوگ را استاندارد می‌کند، اما جایگزین مستندسازی مهندسی یا درک عمیق توسعه‌دهنده نمی‌شود.

### ۴.۷. تفکیک مسئولیت‌ها و پرهیز از ادعای بیش از حد (Separation of Concerns without Overclaiming)
* پروتکل MCP می‌تواند بخش‌هایی از منطق یکپارچه‌سازی، نگاشت فراخوانی‌ها و ترجمه پارامترها را درون سرور MCP کپسوله و متمرکز سازد و تفکیک وظایف (Separation of Concerns) میان تیم‌های هوش مصنوعی و سرویس‌های سازمانی را به شکلی چشمگیر بهبود بخشد.
* **پرهیز از اغراق فنی:** با این وجود، نباید ادعا شود که توسعه‌دهندگان دیگر با جزییات HTTP یا احراز هویت سروکار ندارند یا MCP این بار را خودبه‌خود محو می‌کند. الزامات بنیادین شامل احراز هویت (Authentication)، مجوزدهی و کنترل سطح دسترسی (Authorization)، مدیریت امن کلیدها و اعتبارات (Credential Handling)، اشاعه هویت کاربر نهایی (Identity Propagation)، اعمال مجوزهای سامانه‌های بک‌اند (Backend Permissions)، و پایش و نگهداری عملیاتی (Operational Maintenance) همچنان پابرجا و ضروری هستند و باید به شکلی ساختاریافته در لایه‌های مربوطه پیاده‌سازی و مدیریت گردند.

## ۵. سناریوی مقایسه‌ای محوری: اتصال مستقیم API در برابر MCP

### معماری الف: اتصال مستقیم به API (Direct API Integration)
در این معماری، تیم توسعه‌دهنده برنامه هوش مصنوعی (مثلاً یک دستیار کدنویسی یا چت‌بات شرکتی)، کد اختصاصی برای اتصال به API انبار می‌نویسد. **تصریح قطعی بر مسئولیت اجرایی هاست:** مدل زبانی (LLM) هرگز درخواست‌های شبکه یا HTTP را مستقیماً اجرا نمی‌کند؛ مدل صرفاً قصد ساختاریافته خود را تولید کرده و برنامه میزبان (Host) دریافت‌کننده آن است که اجرای آداپتور سفارشی را هماهنگ می‌نماید:

```
┌────────────────────────────────────────────────────────┐
│               AI Host / Application                    │
│                                                        │
│  [LLM Core]                                            │
│      │                                                 │
│      ▼ (تولید ساختار قصد فراخوانی ابزار / Function Call)  │
│  [Host Application Runtime]                            │
│      │                                                 │
│      ▼ (هماهنگی اجرا توسط هاست - مدل به شبکه وصل نمی‌شود) │

│      • API Key & Credential Handling                   │
│      • Response & Error Parser                         │

              └─────────────┬─────────────┘
```

* **مسئولیت‌های توسعه‌دهنده برنامه در معماری الف:**
  1. نوشتن کاتالوگ ابزار مطابق فرمت اختصاصی مدل زبانی مورد استفاده درون برنامه میزبان.
  2. ایجاد درایور HTTP اختصاصی (`Host-side Integration Adapter`) برای ساخت درخواست به `GET /api/v1/inventory/NVMe-4TB`.
  3. مدیریت دستی هدرهای احراز هویت و کلیدهای دسترسی (`Authorization: Bearer ...`).
  4. پارس کردن کدهای وضعیت HTTP (مانند 200, 404, 500) و تبدیل ساختار پاسخ به متنی که مدل متوجه شود.
  5. **چالش کلیدی:** اگر فردا ابزار دیگری مانند Claude Desktop یا Cursor بخواهد از همین انبار استفاده کند، باید تمامی این مراحل و کدهای آداپتور از ابتدا در آن برنامه تکرار شود!

### معماری ب: اتصال مبتنی بر لایه سرور MCP (MCP-Based Integration)
در این معماری، همان REST API موجود و همان پایگاه داده به قوت خود باقی می‌مانند؛ اما یک سرور سبک MCP به عنوان واسط استاندارد تعریف می‌شود. هاست با داشتن یک کلاینت عمومی MCP می‌تواند با سرور تعامل کند:

```
┌────────────────────────────────────────────────────────┐
│               AI Host / Application                    │
│                                                        │
│  [LLM Core]                                            │
│      │                                                 │
│      ▼ (تولید ساختار قصد فراخوانی ابزار / Function Call)  │
│  [Host Application Runtime]                            │
│      │                                                 │
│      ▼ (اینترفیس استاندارد کلاینت پروتکل)              │
│  [MCP Client]                                          │
│      (پیاده‌سازی عمومی و بازاستفاده‌پذیر پروتکل)        │
└───────────────────────────┬────────────────────────────┘
                            │ JSON-RPC 2.0 (tools/call: query_inventory)
                            ▼
              ┌───────────────────────────┐
              │   Warehouse MCP Server    │
              │   • Exposes Tools Schema  │
              │   • Internal REST Adapter │
              └─────────────┬─────────────┘
                            │ Internal HTTP GET /api/v1/inventory/NVMe-4TB
                            ▼
              ┌───────────────────────────┐
              │   Inventory REST API      │
              │   (Existing - UNCHANGED!) │
              └─────────────┬─────────────┘
                            │ SQL Query
                            ▼
              ┌───────────────────────────┐
              │     Warehouse Database    │
              │  Record: 6 units (NVMe-4TB)│
              │  Inventory ID: INV-2026-981│
              └───────────────────────────┘
```

* **نقاط قوت معماری ب:**
  1. **REST API سازمان دست‌نخورده باقی می‌ماند:** هیچ نیازی به تغییر کنترلرها، روت‌ها یا امنیت وب‌سرویس فعلی انبار نیست.
  2. **کلاینت استاندارد در هاست:** هاست هوش مصنوعی نیازی به نوشتن آداپتور اختصاصی برای انبار ندارد؛ زیرا از قبل پروتکل استاندارد MCP Client را پیاده کرده است.
  3. **قابلیت استفاده مجدد سراسری (Reusability):** هر هاست سازگار با MCP (مانند Claude Desktop، یک محیط IDE، یا یک ایجنت پایتونی) بدون نوشتن ۱ خط کد اتصال اختصاصی جدید، می‌تواند سرور انبار را به عنوان یک منبع یا ابزار متصل کند.
  4. **کپسوله‌سازی منطق اتصال بدون اغراق امنیتی:** منطق اتصال در سرور MCP متمرکز می‌شود؛ با این حال، احراز هویت، اعتبارات و مجوزهای بک‌اند همچنان نیازمند اعمال و نگهداری مهندسی هستند.

### بخش ۰۶.۲: مفهوم API چیست و چه مساله‌ای را حل می‌کند؟ (What Is an API?)

#### الف) متادیتای بخش
* **شناسه:** `section-06-2-what-is-api`
* **مدت زمان:** ۳۵ ثانیه
* **پرسش محوری:** API در معنای کلی چیست و سبک REST چه جایگاهی در منظومه اینترفیس‌ها دارد؟

#### ب) محتوای روی صفحه (On-Screen Content)
* **نشان بالایی (Badge):** `بخش ۶.۲ • ادبیات معماری`
* **تیتر اصلی:** آناتومی <span className="font-mono text-cyan-300" dir="ltr">API</span>: از قرارداد کلی نرم‌افزاری تا سبک‌های وب
* **کارت تفکیک دوگانه مفهومی و اعتبارسنجی قراردادها:**
  1. **مفهوم عام API (Application Programming Interface):** قراردادی صریح برای تعامل قطعات نرم‌افزاری؛ شامل APIهای سیستمی (POSIX, Win32)، کتابخانه‌ها، SDKها، GraphQL، gRPC و وب‌سرویس‌ها.
  2. **سبک معماری REST (Representational State Transfer):** یک سبک معماری فرموله‌شده توسط روی فیلدینگ در سال ۲۰۰۰ بر پایه منابع (Resources)، شناسه‌های یکتا (URI) و تعاملات استاندارد بدون حالت؛ نه صرفاً مجموعه‌ای از متدهای HTTP و آدرس‌های اینترنتی.
  3. **قراردادهای استاندارد و مشخصات OpenAPI:** وب‌سرویس‌های REST سال‌هاست که با استانداردهایی چون OpenAPI (OAS) توصیف ماشین‌خوان و مستندات غنی دارند؛ چالش اصلی در عصر هوش مصنوعی فقدان مستندات نیست، بلکه تکثیر کدهای اتصال اختصاصی و نبود پروتکل تعاملی دینامیک در سطح ایجنت‌هاست.
* **معرفی API انبار پروژه (Inventory REST API Contract):**
  - نقطه انتهایی فرضی مستندسازی‌شده با مشخصات OpenAPI:
    `GET /api/v1/inventory/{sku}`
  - نمونه پاسخ درخواستی:
    ```json
    {
      "sku": "NVMe-4TB",
      "in_stock": true,
      "quantity": 6,
      "inventory_id": "INV-2026-981"
    }
    ```
* **اصل کلیدی:** وب‌سرویس انبار کار خود را با بالاترین کیفیت انجام می‌دهد و برای برنامه‌های سنتی وب عالی است؛ اما ورود برنامه‌های هوش مصنوعی دینامیک، چالش‌های جدیدی ایجاد می‌کند.

#### ج) یادداشت تفصیلی سخنران به زبان فارسی (Presenter Notes)
> «بیایید ابتدا تعریف دقیق API را مرور کنیم تا دچار خطای اصطلاحی نشویم. API یعنی قرارداد برنامه‌نویسی نرم‌افزار. هر رابطه‌ای که در آن یک ماژول به ماژول دیگر می‌گوید 'اگر این تابع را با این ورودی صدا بزنی، این خروجی را دریافت می‌کنی'، یک API است. REST یکی از مشهورترین سبک‌های معماری در وب است که روی فیلدینگ آن را معرفی کرد و فراتر از صرفاً چند متد HTTP است. این وب‌سرویس‌ها با استانداردهایی مثل OpenAPI کاملاً مستند و ماشین‌خوان هستند. در سناریوی آموزشی ما، انبار یک وب‌سرویس تمیز با آدرس GET /api/v1/inventory/{sku} دارد که اگر شناسه NVMe-4TB را به آن بفرستیم، موجودی ۶ عدد و شناسه INV-2026-981 را بازمی‌گرداند. این سیستم کاملاً بی‌نقص است و سال‌هاست به درستی کار می‌کند. اما وقتی پای مدل‌های زبانی به میان می‌آید، تکثیر کدهای اتصال اختصاصی در برنامه‌های مختلف چه چالش‌هایی ایجاد می‌کند؟»

### بخش ۰۶.۳: چالش اتصالات مستقیم و مکرر در عصر هوش مصنوعی (The Integration Problem)

#### الف) متادیتای بخش

* **مدت زمان:** ۴۰ ثانیه
* **پرسش محوری:** چرا ساخت اتصالات مستقیم اختصاصی میان برنامه‌های هوش مصنوعی و سرویس‌ها منجر به چالش مقیاس‌پذیری می‌شود؟

#### ب) محتوای روی صفحه (On-Screen Content)
* **نشان بالایی (Badge):** `بخش ۶.۳ • چالش مقیاس‌پذیری`
* **تیتر اصلی:** مسئله اتصالات اختصاصی چندگانه: چالش مفهومی <span className="font-mono text-amber-300" dir="ltr">M × N</span>
* **نمایش بصری آشفتگی اتصالات سنتی (Custom Connector Spaghetti):**
  - سه برنامه هوش مصنوعی فرضی: Claude Desktop, Cursor IDE, Autonomous Agent.
  - سه سرویس سازمانی: انبار سخت‌افزار (Inventory API)، پایگاه اسناد (Knowledge Base)، و سامانه صدور تیکت (Support API).
  - خطوط درهم‌تنیده: در اتصال کامل، ۹ رابطه ارتباطی ران‌تایم وجود دارد و در روش سنتی، هر برنامه نیازمند آداپتور اختصاصی، درایور احراز هویت، و پارسر خطای مجزاست (۹ کد چسباننده سفارشی).
* **تفکیک علمی روابط زمان اجرا از پیاده‌سازی‌های قابل استفاده مجدد:**
  - **روابط ران‌تایم:** در یک شبکه کامل ۳ هاست و ۳ سرور، تعداد اتصالات فعال همواره $3 \times 3 = 9$ کانال منطقی است؛ پروتکل این اتصالات را محو نمی‌کند.
  - **واحدهای پیاده‌سازی:** در معماری MCP، به جای ۹ کد چسباننده دست‌ساز، ۳ پیاده‌سازی کلاینت و ۳ سرور مستقل ($M+N=6$ پیاده‌سازی استاندارد) همان ۹ اتصال را بدون تکرار کد میزبانی می‌کنند.
* **مشکلات سه‌گانه اتصالات سفارشی:**
  1. **تکثیر شدید کدهای چسباننده (Glue Code Duplication):** هر کلاینت باید مجدداً کدهای نگاشت درخواست و پاسخ بنویسد.
  2. **پراکندگی احراز هویت و مجوزها:** تنظیم تکراری توکن‌ها، کلیدها و سطوح دسترسی در هر برنامه جداگانه.
  3. **هزینه نگهداری فزاینده (Maintenance Overhead):** با تغییر کوچک در شمای یکی از APIها، باید کانکتورهای متعدد در تک‌تک برنامه‌های هوش مصنوعی به‌روزرسانی شوند.
* **نکته علمی آموزشی الزامی (Visible Disclaimer):** «مدل M×N یک مدل مفهومی و آموزشی برای درک مسئله تکثیر کدهای سفارشی است، نه یک قانون قطعی ریاضی. تعداد دقیق پیاده‌سازی‌ها تابع معماری، گیت‌وی‌ها و بازاستفاده از کتابخانه‌هاست.»

#### ج) یادداشت تفصیلی سخنران به زبان فارسی (Presenter Notes)
> «تصور کنید در سازمان شما، ۳ ابزار مختلف مبتنی بر هوش مصنوعی فعال هستند: دستیار درون IDE، چت‌بات دسکتاپ، و یک ایجنت مستقل. از طرف دیگر، ۳ سرویس مستقل شامل انبار، پایگاه دانش و سامانه تیکت داریم. در روش سنتی اتصالات سفارشی، برای برقراری ارتباط کامل میان این‌ها، باید ۹ کد چسباننده و آداپتور مجزا توسط تیم‌های مختلف نوشته شود؛ هر تیم دوباره هدرهای HTTP، مدیریت کلیدها و پارس کردن خطاها را پیاده می‌کند. این مسئله مشهور M در N است. دقت کنید که در زمان اجرا، همچنان ۹ رابطه ارتباطی میان برنامه‌ها و سرویس‌ها برقرار است؛ اما با معماری استاندارد MCP، به جای ۹ پیاده‌سازی پراکنده و شکننده، ۳ پیاده‌سازی کلاینت استاندارد و ۳ سرور مستقل داریم که همگی زبان مشترکی دارند. این یک مدل مفهومی برای درک صرفه‌جویی در توسعه و نگهداری است.»

| مولفه در معماری | نقش در اتصال مستقیم (معماری الف) | نقش در اتصال مبتنی بر MCP (معماری ب) | وضعیت تغییر |

#### ج) یادداشت تفصیلی سخنران به زبان فارسی (Presenter Notes)
> «به این اسلاید بسیار دقیق نگاه کنید؛ این مهم‌ترین قاب کل فصل است. در سمت راست معماری اتصال مستقیم سنتی را می‌بینید: مدل زبانی فراخوانی تابع را پیشنهاد می‌دهد، اما برنامه میزبان باید با یک آداپتور اختصاصی درخواست HTTP به انبار بفرستد. در سمت چپ، معماری مبتنی بر MCP را می‌بینید. به دو مولفه پایینی دقت کنید: پایگاه داده انبار و حتی خودِ Inventory REST API کاملاً دست‌نخورده باقی مانده‌اند! ما وب‌سرویس انبار را حذف نکرده‌ایم. اتفاقی که افتاده این است که یک لایه سرور سبک MCP جلوی آن قرار گرفته است. این سرور، خروجی‌های REST API را می‌خواند و آن‌ها را در قالب متدهای استاندارد MCP اکسپوز می‌کند. هاست هم از کلاینت استاندارد خود استفاده می‌کند. البته توجه داشته باشید که MCP وظایف امنیتی مثل احراز هویت و مجوزها را محو نمی‌کند، بلکه آن‌ها را در لایه‌ای مشخص و متمرکز قرار می‌دهد.»

* **نشان بالایی (Badge):** `بخش ۶.۶ • راهنمای تصمیم‌گیری مهندسی`
* **تیتر اصلی:** ماتریس انتخاب: چه زمانی <span className="font-mono text-emerald-300" dir="ltr">Direct API</span> و چه زمانی <span className="font-mono text-cyan-300" dir="ltr">MCP</span>؟
* **کادرهای دوگانه راهنمای مهندسی (Decision Guidance Matrix):**
  - **چه زمانی اتصال مستقیم API (Direct API) گزینه بهتری است؟**
    * هنگامی که تنها یک برنامه مشخص هوش مصنوعی به یک وب‌سرویس اختصاصی متصل می‌شود.
    * زمانی که پروژه کوچک و موقتی است و ایجاد لایه سرور MCP سربار مهندسی غیرضروری دارد.
    * زمانی که حساسیت تاخیر پکت‌ها در حد چند میلی‌ثانیه مطرح است و لایه واسط اضافه نمی‌خواهیم.
    * زمانی که به اشتراک‌گذاری قابلیت با سایر کلاینت‌ها هیچ ارزش تجاری ندارد.
  - **چه زمانی استفاده از MCP (MCP-Based Integration) ارزش افزوده قطعی دارد؟**
    * زمانی که چند کلاینت سازگار هوش مصنوعی (IDE، چت‌بات، ایجنت) باید به یک قابلیت دسترسی یابند.
    * هنگامی که قابلیت کشف خودکار (Discovery)، ابزارها و منابع در یک اکوسیستم مشترک مورد نیاز است.
    * زمانی که ترکیب‌پذیری چند سرور (Multi-Server Composition) در یک هاست اهمیت دارد.
    * زمانی که تفکیک وظایف تیم هوش مصنوعی از تیم توسعه سرویس‌های بک‌اند اولویت دارد.
* **جمله جمع‌بندی طلایی فصل ششم:**
  > «**API سرویس را عرضه می‌کند؛ اما MCP نحوه اتصال استاندارد برنامه‌های هوش مصنوعی به قابلیت‌های سرور را فرمول‌بندی می‌نماید.**»
  *(APIs expose the services; MCP standardizes how AI applications connect to those capabilities.)*
* **دکمه دعوت به اقدام نهایی (Final CTA to Chapter 07):**
  «ورود به فصل هفتم: قابلیت‌های سه‌گانه سرور MCP (منابع، پرامپت‌ها و ابزارها)»

#### ج) یادداشت تفصیلی سخنران به زبان فارسی (Presenter Notes)
> «در مهندسی نرم‌افزار، هیچ ابزاری چکش طلایی برای حل همه مشکلات نیست. اگر شما در حال ساخت یک اسکریپت ساده پایتون برای خودتان هستید که فقط قرار است از یک API آب‌وهوا استفاده کند، ساختن سرور MCP شاید سربار بی‌مورد باشد؛ اتصال مستقیم بنویسید و کار را تمام کنید! اما اگر در یک سازمان هستید که می‌خواهید دسترسی به پایگاه داده مشتریان یا انبار را برای انواع دستیارهای توسعه‌دهندگان، تحلیل‌گران و ایجنت‌های مستقل باز کنید، ساخت یک سرور MCP باعث می‌شود یک بار برای همیشه این اتصال را بسازید و هر کلاینت سازگاری بتواند بی‌درنگ از آن بهره‌مند شود. جمع‌بندی طلایی ما این است: API سرویس را عرضه می‌کند، و MCP اتصال هوش مصنوعی به آن را استاندارد می‌سازد. در فصل هفتم، سه قابلیت بنیادین این سرورها یعنی منابع، پرامپت‌ها و ابزارها را با هم بررسی خواهیم کرد.»

## ۷. نیازمندی‌های طراحی تعاملی و ویجت‌های آموزشی (Interactive Design Specifications)

برای پیاده‌سازی فصل ۶ در تسک آتی (`TASK-006.2`)، سه ویجت تعاملی آموزشی زیر پیش‌بینی و طراحی شده‌اند:

### ۷.۱. ویجت تعویض‌گر معماری مقایسه‌ای (`ArchitectureComparisonSwitcher`)

* **عناصر متغیر در سوئیچ:**
  - نودهای معماری و برچسب‌های مسئولیت:
    * در حالت مستقیم: `AI Host / Application ──► Host-side Integration Adapter ──► Inventory REST API ──► Database` (با تاکید بر اینکه مدل خود درخواست HTTP را اجرا نمی‌کند و هاست وظیفه هماهنگی آداپتور را دارد).
    * در حالت MCP: `AI Host / Application ──► MCP Client ──► Warehouse MCP Server ──► Inventory REST API ──► Database`.
  - رنگ کادرهای مرزی (قرمز/کهربایی برای کدهای چسباننده در اتصال مستقیم، سبز/آبی فیروزه‌ای برای سرور استاندارد MCP).
  - متن تشریحی نقاط قوت و ضعف هر رویکرد با تاکید بر عدم اغراق در حذف وظایف امنیتی.

### ۷.۲. نمایشگر کاهش اتصالات تکراری (`IntegrationMatrixDemo`)
* **هدف آموزشی:** نمایش بصری اتصال ۳ برنامه هوش مصنوعی به ۳ سرویس خارجی با تفکیک دقیق اتصالات زمان اجرا از واحدهای پیاده‌سازی:
  - **اتصالات ران‌تایم (Runtime Connections):** در هر دو حالت، هنگامی که هر ۳ برنامه به هر ۳ سرویس متصل هستند، ۹ خط ارتباطی منطقی فعال در زمان اجرا ترسیم می‌شود (هرگز به صورت گمراه‌کننده تنها ۳ خط ران‌تایم ترسیم نمی‌شود).
  - **حالت ۱ (اتصالات اختصاصی سنتی — $M \times N$):** نمایش ۹ خط اتصال با خطوط درهم‌تنیده با برچسب «۹ کد چسباننده و پیاده‌سازی اختصاصی ناهماهنگ».
  - **حالت ۲ (اکوسیستم مبتنی بر MCP — $M + N$):** همان ۹ ارتباط ران‌تایم از طریق ۳ پیاده‌سازی کلاینت استاندارد در هاست‌ها و ۳ سرور مستقل MCP برقرار می‌شود (۶ واحد پیاده‌سازی استاندارد و بازاستفاده‌پذیر).
* **برچسب الزامی سلب ادعای ریاضی (Visible Educational Disclaimer):**
  «مدل مفهومی آموزشی؛ نمایش ساده‌سازی‌شده کاهش افزونگی در واحدهای پیاده‌سازی ($M+N$ پیاده‌سازی مستقل در برابر $M \times N$ کد سفارشی)، نه کاهش اتصالات اجرایی در زمان ران‌تایم. در سناریوی اتصال کامل، تعداد کانال‌های ارتباطی منطقی زمان اجرا همچنان ۹ اتصال است.»

## ۸. جدول تدقیق محتوا و واژه‌نامه تخصصی (Glossary & Terminology)

| واژه انگلیسی | معادل فارسی مصوب در ارائه | تعریف دقیق فنی در بافت فصل |
|---|---|---|
| **API** | رابط برنامه‌نویسی کاربردی | اینترفیس یا قراردادی که به نرم‌افزارها اجازه تعامل بدون آگاهی از کدهای درونی را می‌دهد. |
| **REST** | سبک معماری انتقال وضعیت بازنمودی | یکی از سبک‌های طراحی API در وب بر مبنای منابع، URIها و متدهای HTTP. |
| **MCP Server** | سرور پروتکل زمینه مدل | آداپتور مستقل نرم‌افزاری که قابلیت‌های ابزاری، داده‌ای یا پرامپت را در قالب پروتکل استاندارد MCP عرضه می‌کند. |
| **Function Calling** | فراخوانی تابع توسط مدل زبانی | سازوکار درون‌مدلی که بر اساس پرامپت، شیء ساختاریافته نام ابزار و ورودی‌ها را تولید می‌کند. |
| **Ad-hoc Connector** | اتصال اختصاصی و سفارشی | کدهای دست‌نویس چسباننده که یک برنامه خاص را مستقیماً به یک API وصل می‌کنند و قابل استفاده مجدد نیستند. |
| **Adapter Pattern** | الگوی طراحی آداپتور | الگوی ساختاری شیءگرا که به کلاس‌های با اینترفیس‌های ناسازگار اجازه همکاری می‌دهد (نقش سرور MCP روی APIهای سنتی). |
| **Glue Code** | کدهای چسباننده | کدهای تکراری نگاشت، اعتبارسنجی و تبدیل ساختارهای داده‌ای که هیچ ارزش منطق بیزینس جدیدی ندارند. |

## ۹. پل اتصال و انتقال میان فصول (Transitions)

* **انتقال از فصل پنجم به ششم:**
  در انتهای فصل پنجم، کاربر مشاهده کرد که سرور انبار برای پاسخ به متد `tools/call`، یک کوئری به دیتابیس زد و پاسخ ۶ قطعه NVMe-4TB را برگرداند. سوال بلافاصله‌ای که در ذهن مخاطب نقش می‌بندد این است که «چرا از همان REST API موجود استفاده نکردیم و چرا به MCP نیاز داشتیم؟»؛ فصل ششم مستقیماً از این نقطه آغاز می‌شود.
* **انتقال از فصل ششم به هفتم:**
  در انتهای فصل ششم ثابت می‌شود که سرور MCP یک درگاه استاندارد برای قابلیت‌های خارجی است. اما یک سرور MCP چه قابلیت‌هایی را می‌تواند عرضه کند؟ فصل هفتم با معرفی سه ضلع مثلث سرورهای MCP (منابع Resources، پرامپت‌ها Prompts و ابزارها Tools) ادامه خواهد یافت.
