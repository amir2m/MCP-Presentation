## «شبیه‌سازی جریان یک درخواست در MCP»
### (Request Lifecycle Simulation: From User Query to Tool Execution and Final Response)

## ۱. یافته‌های معماری سیستم و پیش‌نیازهای پروژه (System Architecture Findings)

فصل پنجم، نقطه عطف عملیاتی پرزنتیشن است که مفاهیم نظری فصل ۴ را در بستر یک سناریوی تعاملی به نمایش می‌گذارد. بررسی کدهای فصول قبلی (به‌ویژه شبیه‌سازهای فصل ۱ و ۲ و ساختار ماژولار فصل ۴) نشان می‌دهد که:

1. **پیوستگی سناریو با فصول قبل:** سناریوی استعلام قطعه سخت‌افزاری <span className="font-mono text-cyan-300" dir="ltr">NVMe-4TB</span> قبلاً در فصل اول به عنوان مثال انگیزاننده مطرح شده است؛ بنابراین در فصل پنجم از همان قطعه و همان متد (`query_inventory`) برای حفظ یکپارچگی ذهنی مخاطب استفاده خواهد شد.
2. **مدل رندر دوگانه (Dual Rendering Mode):**
   - **Presentation Mode (اسلاید‌محور):** ۶ اسلاید مجزا با قابلیت جابه‌جایی از طریق کلیدهای ناوبری یا منوی سرفصل‌ها، که هر اسلاید بر یکی از فازهای چرخه حیات متمرکز است.
   - **Scroll Mode (اسکرول پیوسته):** رندر متوالی هر ۶ بخش در قالب یک روایت داستانی منسجم همراه با فاصله‌گذاری مناسب (`space-y-24`).
3. **موتور شبیه‌سازی ماژولار (Simulation Engine):** به جای تکثیر کدهای انیمیشن و وضعیت در هر بخش، یک کامپوننت هسته شبیه‌ساز تعاملی (`RequestLifecycleSimulator.tsx`) طراحی می‌شود که قابلیت استفاده در اسلایدها و حالت اسکرول را به شکل هماهنگ داراست.

### ۳.۵. بخش ۵.۴: `ToolExecutionSection.tsx`
* **مسیر فایل:** `src/components/chapters/chapter05/ToolExecutionSection.tsx`
* **مسئولیت‌ها:**
  * تحلیل گام‌های سه‌گانه سرور MCP: اعتبارسنجی پروتکل و `_meta`، بررسی ورودی ابزار، و فراخوانی لاجیک هندلر.
  * مرزبندی شفاف میان سرور پروتکل (MCP Server) و پایگاه داده انبار (External Database).
  * تبیین اصل عدم وابستگی پروتکل به SQL یا پایگاه‌داده (Database Agnostic): پروتکل MCP دستور SQL اجرا نمی‌کند؛ سرور می‌تواند به فایل، REST API یا CLI وصل شود.
  * نمایش کوئری نمونه داخلی سیستم خارجی با برچسب رسمی: `اجرای داخلی سرور — پیاده‌سازی نمونه ابزار (Server Internal Execution — Illustrative Implementation)`.
  * کالبدشکافی لایه‌های شش‌گانه تعامل:
    1. لایه خواست کاربر (User Intent)
    2. لایه فراخوانی ابزار مدل در API هاست (LLM Tool Call)
    3. لایه فریم پیام استاندارد JSON-RPC پروتکل MCP (`tools/call` با `_meta`)
    4. لایه پردازش و اجرای هندلر در سرور MCP
    5. لایه اتصال به منبع داده خارجی (External DB via SQL Driver)
    6. لایه بازگشت داده خام و بسته‌بندی در قالب فریم `result` پروتکل MCP.
  * تبیین الگوهای اعلان پیشرفت در کارهای طولانی‌مدت (`notifications/progress`).
  * یادداشت ارائه‌دهنده و جمله انتقال به بخش بعدی.

### ۳.۶. بخش ۵.۵: `ResultHandlingSection.tsx`
* **مسیر فایل:** `src/components/chapters/chapter05/ResultHandlingSection.tsx`
* **مسئولیت‌ها:**
  * تحلیل ساختار شیء نتیجه استاندارد بازگشتی مطابق نسخه `2026-07-28` حاوی `"resultType": "complete"` و آرایه `content`.
  * پیاده‌سازی ماتریس تدقیق علمی سناریوهای چهارگانه پاسخ و خطا:
    1. **سناریوی الف (موفق با موجودی کالا):** اجرای سالم، `quantity: 6`، `in_stock: true`، بدون پرچم خطا.
    2. **سناریوی ب (موفق با موجودی صفر):** اجرای سالم، `quantity: 0`، `in_stock: false` — تبیین این که موجودی صفر یک پاسخ معتبر داده‌ای است و به عنوان شکست اجرای ابزار تلقی نمی‌شود (عدم فعال‌سازی `isError`).
    3. **سناریوی ج (خطای سطح اجرای ابزار):** طبق استاندارد MCP، توصیه پروتکلی (SHOULD) مبنی بر بازگرداندن فریم معتبر JSON-RPC با شیء `result` حاوی `"resultType": "complete"`، فیلد `isError: true` و متن خطای پایگاه داده در `content`.
    4. **سناریوی د (خطای متد ناشناخته پروتکل):** شیء استاندارد JSON-RPC `error` با کد اختصاصی `-32601 Method not found` (منحصراً برای متد ناشناخته یا پشتیبانی‌نشده و تفکیک‌شده از خطاهای نحوی `-32700 Parse error` و درخواست نامعتبر `-32600 Invalid Request`).
  * اثبات این که موفقیت پروتکل متضمن صحت داده‌های تجاری نیست.
  * انتقال داده از طریق کلاینت به هاست و ادغام در کانتکست مدل زبانی.
  * یادداشت ارائه‌دهنده و جمله انتقال به بخش بعدی.

### ۳.۸. کامپوننت هسته تعاملی: `RequestLifecycleSimulator.tsx`
* **مسیر فایل:** `src/components/chapters/chapter05/RequestLifecycleSimulator.tsx`
* **مسئولیت‌ها:**
  * پیاده‌سازی گره‌های معماری با مرزبندی واضح:
    - هاست برنامه میزبان (Host Application) که کلاینت MCP را به عنوان آداپتور داخلی در بر دارد.
    - ارتباط مدل زبانی منحصراً با هاست (بدون هیچ خط ارتباطی به سرور یا دیتابیس).
    - کلاینت MCP در هاست که از طریق JSON-RPC 2.0 با سرور MCP صحبت می‌کند.
    - سرور MCP که از طریق درایور داخلی با دیتابیس خارجی تعامل دارد.
  * کنترل‌های ناوبری چرخه حیات: Play / Pause, Next Step, Previous Step, Reset / Replay.
  * انیمیشن جریان پالس سیگنال پیام میان گره‌های فعال با `motion/react`.
  * سوئیچ تعاملی سناریوهای چندگانه:
    - **شاخه الف (Happy Path — In-Stock):** استعلام موفق با موجودی ۶ عدد.
    - **شاخه ب (Happy Path — Zero-Stock):** استعلام موفق با موجودی ۰ عدد (داده معتبر تجاری بدون فعال‌سازی `isError`).
    - **شاخه ج (Tool Failure Branch):** خطای زمان انقضای دیتابیس با بازگشت `result.isError: true`.
    - **کادر دمو خطای پروتکل (Protocol Error Demo):** نمایش خطای متد ناشناخته `-32601 Method not found`.
  * هماهنگی با ویجت دیباگر بارهای داده‌ای (`PayloadDebugger`).

### ۳.۹. ویجت بازرسی داده‌ها: `PayloadDebugger.tsx`
* **مسیر فایل:** `src/components/chapters/chapter05/PayloadDebugger.tsx`
* **مسئولیت‌ها:**
  * نمایش تفکیک‌شده و استاندارد بارهای داده‌ای در ۶ لایه شفاف معماری:
    1. **User Text:** پرامپت خام کاربر به زبان طبیعی.
    2. **Model Tool Call (Illustrative Model Tool-Calling Representation):** خروجی نمونه مدل در ساختار رابط فراخوانی ابزار Host-LLM (وابسته به API ارائه‌دهنده مدل، متمایز از پیام MCP JSON-RPC، و منشأ ساخت پیام مجزای tools/call توسط کلاینت MCP).
    3. **MCP Request:** پیام رسمی JSON-RPC 2.0 برای `tools/call` همراه با متادیتای الزامی `_meta`.
    4. **Server Internal Execution:** کوئری نمونه SQL اجرا شده در سیستم خارجی (با برچسب صریح پیاده‌سازی نمونه).
    5. **MCP Response:** شیء استاندارد `result` با `"resultType": "complete"` یا پرچم `isError: true`، و مقایسه با شیء `error` پروتکل.
    6. **Final Synthesis:** پاسخ نهایی روان و طبیعی تولیدشده توسط مدل برای کاربر.
  * امکان کپی کردن آسان محتوای JSON به کلیپ‌بورد با فیدبک بصری.
  * استایل کامپکت دارک با جهت‌گیری استاندارد LTR برای کدهای فنی.

## ۵. راهبرد واکنش‌گرایی، RTL و دسترسی‌پذیری (Responsive & Accessibility Strategy)

1. **طراحی واکنش‌گرا در ۴ اندازه صفحه:**
   * **Desktop (1440×900 & 1366×768):** نمایش کامل گره‌های معماری در چیدمان دوبعدی افقی و نمایش هم‌زمان دیاگرام جریان پیام و پنجره دیباگر.
   * **Tablet (768×1024):** تبدیل گره‌ها به ماتریس ۲×۳ متوازن همراه با حفظ فلش‌های متحرک جریان.
   * **Mobile (390×844):** چیدمان گره‌ها به صورت عمودی (Vertical Timeline) با کنترل‌های لمسی متراکم و تب‌های اسکرول‌پذیر افقی برای دیباگر داده‌ها بدون هیچ‌گونه Horizontal Page Overflow.
2. **جهت‌گیری متن و ایزولاسیون کدها:**
   * زبان اصلی ارائه فارسی (RTL) با ساختار فونت یکنواخت است.
   * تمام قطعات کد JSON، کوئری‌های SQL، اسامی متدها و مقادیر فراداده در کانتینرهای با کلاس `dir="ltr"` و فونت مونواسپیس ایزوله می‌شوند.
3. **پشتیبانی از کاهش حرکت (Reduced Motion):**
   * برای کاربرانی که تنظیمات `prefers-reduced-motion` دارند، انیمیشن‌های جابه‌جایی پالس خاموش شده و تغییر وضعیت‌ها با Fade ساده انجام خواهد گرفت.
4. **دسترس‌پذیری صفحه‌کلید (Keyboard Accessibility):**
   * کلید Space: پخش یا توقف شبیه‌ساز.
   * کلیدهای جهت‌نما (Arrow Left / Arrow Right): حرکت به گام بعدی یا قبلی در شبیه‌ساز.

## ۶. طرح یکپارچه‌سازی با سامانه ارائه (System Integration Plan)

در فاز پیاده‌سازی (تسک بعد)، تغییرات زیر در فایل‌های هماهنگ‌کننده سامانه اعمال خواهد شد (در این تسک برنامه‌ریزی شده و اعمال نمی‌گردد):

1. **به‌روزرسانی تعاریف در `src/lib/presentation.ts`:**
   * تغییر وضعیت فصل ۵ از `status: 'planned'` به `status: 'active'`.
